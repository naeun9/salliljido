## 1. 서비스 소개

- **서비스명**: 살릴지도 (Salliljido)
- **서비스 유형**: 웹 서비스 (React + Vite SPA, Vercel Serverless Functions)
- **서비스 개요**: 인구감소지역 29곳에서 며칠~한 달 살아보려는 사람이
  지역을 고르고, 하루 일정과 예상 비용을 만들고, 지자체 체류지원 공고까지
  한 화면에서 확인하는 웹 서비스.
- **주제 선정 이유**:

  "한 달 살기"를 준비하는 사람이 실제로 부딪히는 벽은 정보가 없는 것이
  아니라 **정보가 흩어져 있고, 정작 살아볼 때 필요한 판단 재료가 없다는
  것**이다. 기존 관광 서비스는 "며칠 여행"을 전제로 명소와 맛집을
  보여주지만, 며칠 이상 머무는 사람이 알아야 하는 것은 다르다.

  1. **살 수 있는 곳인지** — 식당과 카페가 몇 곳인지, 얼마나 한적한지,
     서울에서 어떻게 가는지. 여행 정보에는 없는 생활 여건이다.
  2. **얼마가 드는지** — 숙박 형태와 기간에 따라 총액이 크게 달라지는데,
     이를 미리 계산해 주는 서비스가 없다.
  3. **지원받을 수 있는지** — 지자체 체류지원 공고는 시군 홈페이지,
     농업기술센터, 그린대로, 민간 플랫폼에 흩어져 있고 신청 기간이 짧다.
     공고 하나를 놓치면 수십만 원을 그대로 부담한다.

  대상 지역을 **행정안전부가 지정한 인구감소지역**으로 한정한 이유도
  같다. 인구감소지역은 체류 인구 유입이 정책 목표여서 지자체 지원
  프로그램이 실제로 존재하고, 서비스의 안내가 지역에 실질적인 도움이
  된다. 관광 데이터로 "놀러 갈 곳"을 고르는 데서 멈추지 않고,
  **"머물 수 있는 곳"을 판단하는 데까지 쓰는 것**이 이 서비스의 목표다.

### 서비스 핵심기능

- **조건 기반 지역 추천** — 광역(강원·충남·경북) / 체류 기간 / 지내고 싶은
  환경(자연·바다·산·소도시) 3단계를 고르면 인구감소지역 29곳 중 최대 3곳을
  추천한다. 추천 카드의 생활 여건 게이지 3개는 실측 데이터로 계산한다.
- **실측 데이터 기반 지역 소개** — 식당·카페 건수, 하루 평균 방문자 수,
  수도권 기준 교통 접근을 근거로 그 지역의 생활 여건을 문장으로 설명한다.
  지역명 해시 같은 임의 값을 쓰지 않는다.
- **둘러보기(5개 카테고리 × 지도)** — 숙박 / 식당·카페 / 체험 프로그램 /
  주변 관광지 / 걷기 코스를 한국관광공사 API 실시간 호출로 받아 하위 필터와
  카카오맵에 함께 표시하고, 장소를 누르면 상세 정보를 모달로 보여준다.
- **체류 계획 자동 생성·편집과 예상 비용 산정** — 체류 일수만큼 일자별
  아침·점심·저녁 일정을 그 지역 실제 장소로 자동 생성하고, 숙박·식비·이동·
  체험비를 항목별로 계산한다. 최종 계획은 엑셀(.xlsx)과 인쇄로 내보낸다.
- **지자체 체류지원 프로그램 안내** — 신청 기간을 확인한 11건을 유형(체류
  여행 지원 / 귀농귀촌 살아보기)·지역·모집 상태로 걸러 보여주고, 마감일을
  접속 날짜 기준으로 자동 판정한다.

## 2. [선택] 지역 특화 서비스 구현 세부내용

- **특화 지역명**: **해당 없음**
- **구현 내용**:

  해당 없음. 이 항목의 가점 기준은 **하나의 광역자치단체**를 특화 대상으로
  삼는 경우인데, 본 서비스는 강원특별자치도·충청남도·경상북도 **3개 광역**의
  인구감소지역 29곳을 동일한 깊이로 다루므로 기준에 해당하지 않는다.

  3개 광역을 선택한 것은 서비스 구조상의 필요 때문이다. 지역 추천 조건이
  광역 3개 × 환경 4개 = 12가지 조합이고 결과를 3곳까지 보여주기 때문에,
  조합마다 후보가 최소 3곳 있어야 결과 화면이 빈자리 없이 채워진다.
  (상세: `src/data/regions.js` 머리말)

## 3. 서비스 핵심 기능별 흐름도

### 핵심 기능 1

- **기능명**: 조건 기반 지역 추천
- **기능 설명**:

  3단계 질문으로 조건을 받아 인구감소지역 29곳 중 최대 3곳을 추천한다.
  선택 조건은 ① 광역(강원 / 충남 / 경북 / 상관없음) ② 체류 기간(1주 / 2주 /
  1달 / 직접 입력) ③ 지내고 싶은 환경(자연 / 바다 / 산 / 소도시)이다.

  추천 카드에 붙는 생활 여건 게이지 3개(카페 / 식당 / 한적함)는 지역 소개
  화면과 **같은 함수**(`src/services/regionProfile.js`)에서 계산한다. 두
  화면이 각자 점수를 만들면 같은 지역인데 화면마다 다른 말을 하게 되므로
  판정 규칙을 한 곳으로 모았다.

  고른 조건은 브라우저 `localStorage`에 담아, 새로고침하거나 계획 주소로
  바로 들어와도 체류 일수·비용이 기본값으로 되돌아가지 않게 했다.

**[기능 흐름도]**

- **화면 1 설명 — 홈 (`/`)**
  Hero 영역의 "내게 맞는 지역 찾기" 버튼, 서비스 이용 흐름 4단계 안내,
  지역 캐러셀(대표 사진 + 지역명), 지원 프로그램 티저(마감 임박 순 3건),
  마무리 CTA로 구성된다. 지역 캐러셀 카드를 바로 눌러 조건 선택을 건너뛰고
  지역 소개로 갈 수도 있다.

- **화면 2 설명 — 조건 선택 (`/find`)**
  01·02·03 번호가 붙은 3단계 폼이 한 화면에 세로로 놓인다. 각 단계는 칩
  버튼 선택 방식이고, 체류 기간에서 "직접 입력"을 고르면 일수 입력란이
  열린다. 세 단계를 모두 고르면 하단 "지역 추천받기" 버튼이 활성화된다.

- **화면 3 설명 — 추천 결과 (`/find/result`)**
  약 1.1초 스켈레톤을 보여준 뒤 결과가 나타난다. 왼쪽에 추천 지역 카드
  최대 3장(지역명, 추천 이유, 태그, 생활 여건 게이지 3개), 오른쪽에 추천
  지역 위치를 핀으로 찍은 카카오맵 미니맵이 붙는다. 조건에 맞는 지역이
  없으면 조건을 넓히도록 안내하는 빈 상태 화면이 나온다.

- **화면 4 설명 — 지역 소개 (`/region/:regionId`)**
  카드의 "자세히 보기"로 이동한다. 핵심 기능 2에서 설명한다.

### 핵심 기능 2

- **기능명**: 실측 데이터 기반 지역 소개
- **기능 설명**:

  그 지역에서 며칠~한 달 살 때의 생활 여건을 **측정값**으로 설명한다.
  근거는 세 가지다.

  | 항목 | 근거 데이터 | 출처 |
  | --- | --- | --- |
  | 카페 / 식당 여건 | 지역별 관광 콘텐츠 건수 (카페 FD05 / 식사류 FD01~04) | 관광공사 `areaBasedList2` 실측 |
  | 한적함 | 하루 평균 방문자 수 (외지인+외국인) | 관광공사 데이터랩 `locgoRegnVisitrDDList` 실측 |
  | 교통 접근 | 수도권(서울) 출발 주 수단·소요시간 | 29곳 개별 확인 |

  판정 구간은 29곳을 전부 재고 값이 실제로 끊기는 자리로 잡았다. 예를 들어
  한적함 경계는 하루 방문자 2만 명과 4만 명인데, 29곳을 정렬했을 때
  1.5만~2.0만(청송 15,460 → 의성 20,204)과 3.9만~4.7만(문경 39,156 →
  양양 47,456) 사이가 비기 때문이다.

  **말하지 않는 것을 정한 것도 설계의 일부다.** 마트·병원·코워킹 공간은
  관광공사 목록에 없는 정보이므로 있다/없다를 언급하지 않는다. 근거 없는
  문장을 만들지 않기 위한 규칙이다.

**[기능 흐름도]**

- **화면 1 설명 — 지역 소개 배너**
  지역 대표 사진 위에 지역명, 인구감소지역 배지, 선택한 체류 조건(예:
  "2주 · 바다")이 얹힌다. 오른쪽에 지역 저장(하트) 버튼이 있고, 하단에
  "체류 계획 만들기" / "먼저 둘러보기" 두 갈래 버튼이 놓인다.

- **화면 2 설명 — ABOUT 영역**
  위 표의 세 항목을 문장으로 풀어 쓴다. 걷기 코스가 있는 지역에서는
  하이라이트 한 줄이 추가되고, 코스가 없는 지역에서는 그 줄이 통째로
  사라진다(전국 142코스가 해안선·접경을 따라가 내륙 지역에는 코스가 없다).

- **화면 3 설명 — 통계 + 사진 슬라이드**
  숙박·식당·카페·전체 콘텐츠 건수를 수치로 보여주고, 그 옆에서 지역 사진
  4장이 캡션과 함께 크로스페이드로 넘어간다. 사진은 관광공사 관광사진
  정보 API에서 촬영지를 확인해 고른 것이다.

- **화면 4 설명 — 저장 확인 모달**
  지역 저장/해제 시 확인 모달이 뜨고, 저장한 지역은 마이페이지 목록에
  저장 날짜와 함께 남는다.

### 핵심 기능 3

- **기능명**: 둘러보기 — 5개 카테고리 목록과 지도
- **기능 설명**:

  그 지역의 관광 콘텐츠를 한국관광공사 API **실시간 호출**로 받아 5개
  카테고리로 나눠 보여준다.

  | 카테고리 | 분류체계(lclsSystm1) | 하위 필터 |
  | --- | --- | --- |
  | 숙박 | AC | 호텔 / 펜션·민박 / 콘도 / 한옥스테이 / 농어촌민박 / 캠핑·야영장 |
  | 식당·카페 | FD | 한식 / 외국식 / 간이음식 / 카페 / 주점 |
  | 체험 프로그램 | EX | 전통체험 / 공예체험 / 농촌·어촌체험 / 템플스테이 / 웰니스 / 산업관광 |
  | 주변 관광지 | NA·HS·VE·LS | 자연 / 역사 / 문화 / 레저스포츠 |
  | 걷기 코스 | (두루누비) | 3시간 이내 / 반나절 / 하루 |

  **호출 최소화 설계**: 5개 카테고리를 각각 부르면 지역 하나에 5건이
  들지만, 분류체계 대분류로 한 번에 받아 화면에서 나누므로 **지역 진입당
  1건**으로 끝난다. 걷기 코스는 전국 142건이 전부라 서버가 한 번에 다 받아
  12시간 메모리에 두고 지역으로 걸러 주므로, 방문자가 몇 개 지역을 돌아봐도
  상류 호출이 늘지 않는다. (일 1,000건 한도 대응)

  걷기 코스 하위 필터를 난이도가 아니라 **소요시간**으로 만든 것도 실측
  결과다. 파일럿 지역 30개 코스의 난이도별 소요시간 중앙값이 쉬움·보통·
  어려움 모두 270분으로 같아서, 난이도로 걸러도 하루가 얼마나 들어가는지가
  전혀 달라지지 않았다.

**[기능 흐름도]**

- **화면 1 설명 — 둘러보기 탭 (`/region/:regionId/explore` 또는 계획 화면 1번 탭)**
  왼쪽에 카테고리 5개 칩과 하위 필터 칩, 그 아래 장소 카드 목록이 놓인다.
  카드에는 이름, 유형 배지, 주소, 대표 이미지가 들어간다. 오른쪽에 카카오맵
  사이드 지도가 붙어 목록과 같은 장소를 핀으로 찍는다.

- **화면 2 설명 — 지도 연동**
  카드에 마우스를 올리거나 누르면 해당 핀이 강조되고 지도 중심이 이동한다.
  걷기 코스 카테고리에서는 핀 대신 GPX에서 뽑은 경로가 선으로 그려진다
  (코스당 최대 100점으로 솎아 원본 굴곡을 유지하면서 전송량을 줄였다).
  지도 SDK를 못 불러오면 목업 셸과 안내 문구로 폴백한다.

- **화면 3 설명 — 장소 상세 모달**
  카드를 누르면 `detailCommon2` + `detailIntro2`를 동시에 호출해 개요,
  주소, 전화, 홈페이지, 유형별 정보(숙박이면 체크인·주차, 음식점이면
  영업시간·대표메뉴 등)를 모달로 보여준다. 응답에 없는 필드는 칸을 아예
  숨겨 빈 라벨이 남지 않게 했다.

- **화면 4 설명 — 계획에 담기**
  체험 프로그램·식당 카드에서 "담기"를 누르면 체류 계획 탭의 해당 슬롯
  후보로 넘어간다.

### 핵심 기능 4

- **기능명**: 체류 계획 자동 생성·편집과 예상 비용 산정
- **기능 설명**:

  체류 일수만큼 하루 일정을 **그 지역 실제 장소로** 자동 생성하고, 비용을
  항목별로 계산해 최종 계획으로 내보낸다.

  **일정 자동 생성** — 시간대별로 분류체계를 대응시켜 후보를 뽑는다.

  | 시간대 | 뽑는 분류 |
  | --- | --- |
  | 오전 | 카페 (FD05) |
  | 오후 | 주변 관광지(NA·HS·VE·LS) + 체험(EX) |
  | 저녁 | 식당(FD01 한식 / FD02 외국식 / FD03 간이음식 / FD04 주점) |

  생성 결과는 **난수를 쓰지 않는 순수 계산**이다. (일차, 재생성 시드, 테마,
  음식 취향, 목록 순서)만으로 정해지므로 저장한 계획을 다시 열거나 최종
  계획 화면에서 다시 그려도 같은 일정이 나온다.

  **예상 비용 산정** — 숙박은 기간을 구간으로 나눠 구간별 단가를 매길 수
  있고(예: 1~3박은 게스트하우스, 4~14박은 월세형), 식비는 스타일별 1일
  기준액(외식 중심 42,000원 / 반반 30,000원 / 자취 중심 18,000원)에
  "저녁은 숙소에서 직접 요리" 선택을 반영해 그날 식비의 일부를 덜어낸다.
  이동·체험비·기타 항목을 더해 항목별 막대와 총액을 보여준다.

**[기능 흐름도]**

- **화면 1 설명 — 체류 계획 화면 상단 (`/plan/:regionId`)**
  지역명과 계획 이름이 있는 배너 아래에 탭 3개(① 둘러보기 ② 체류 계획
  ③ 예상 비용)가 놓인다. 탭을 옮겨도 같은 계획 상태를 공유한다.

- **화면 2 설명 — 체류 계획 탭**
  일차 탭(1일차, 2일차 …)을 고르면 그 날의 아침·점심·저녁 슬롯 카드가
  나온다. 각 슬롯에 장소명·주소·유형이 들어가고, "다른 곳 보기"로 같은
  분류의 다른 후보로 바꿀 수 있다. 날짜별 테마(힐링 / 레저 / 문화탐방 /
  워케이션)와 음식 취향을 고르면 뽑는 후보가 바뀐다. 오른쪽 사이드 지도에
  그날 동선이 표시된다.

- **화면 3 설명 — 예상 비용 탭**
  숙박(구간 나누기) · 식비(스타일 + 요리 토글) · 이동 · 체험비 · 기타
  섹션이 세로로 놓이고, 맨 아래 항목별 막대 그래프와 총액이 나온다.
  "지원 프로그램 찾아보기" 버튼은 그 지역 광역으로 필터를 미리 걸어
  지원 프로그램 화면으로 넘긴다.

- **화면 4 설명 — 최종 계획 (`/plan/:regionId/overview`)**
  상단에 계획 이름·기간·지표 요약, 지역 한눈에 보기, 전체 일정표(일차별
  전체 타임라인), 비용 요약, 이 지역 지원 프로그램 섹션이 이어진다.
  체류 범위를 보여주는 지도가 함께 붙는다.

- **화면 5 설명 — 내보내기**
  "내보내기" 메뉴에서 **엑셀(.xlsx)** 또는 **인쇄**를 고른다. 엑셀은
  시트 2장(일정: 일차/테마/시간대/장소명/카테고리/주소, 예상 비용:
  항목/금액/근거 + 합계)으로 떨어진다. 인쇄에서는 헤더·버튼·지도·지원
  프로그램 섹션이 자동으로 숨는다.

### 핵심 기능 5

- **기능명**: 지자체 체류지원 프로그램 안내
- **기능 설명**:

  체류 비용을 실제로 줄여 주는 지자체 공고를 모아 보여준다. 현재 **공식
  공고로 확인한 11건**이 들어 있다(그중 1건은 공식 공고 URL을 못 찾아
  "공고 확인 필요"로 표시하고 문의처를 안내한다).

  **유형을 둘로 나눈 것이 핵심이다.** 성격이 전혀 다른 두 갈래가 "한 달
  살기 지원"이라는 이름으로 섞여 있었다.

  | 유형 | 성격 | 건수 | 예 |
  | --- | --- | --- | --- |
  | 체류 여행 지원 | 관광 부서가 여행 경비(숙박·체험·부대비)를 환급. 며칠~한 달 | 8 | 예산 일주일살기, 영덕 치유 이음스테이션 |
  | 귀농귀촌 살아보기 | 농업 부서가 정착을 전제로 숙소와 연수비를 제공. 보통 한 달 이상 | 3 | 영월 강원에서 살아보기, 봉화 봉화愛살래, 의성 농촌에서 살아보기 |

  **모집 상태는 접속 날짜로 자동 판정한다.** 데이터에는 신청 시작일과
  마감일만 적고, 마감 임박(7일 이내) / 모집 중 / 예정 / 마감과 D-day
  문구는 계산해서 만든다. 손으로 상태를 적어 두면 날짜가 지나도 "모집 중"
  으로 남기 때문이다.

  **데이터 수집 원칙** — **신청 기간을 확인한 것만** 넣는다. 모집 상태가
  신청 기간에서 자동으로 나오기 때문에, 기간을 모르면 이미 끝난 사업이
  "상시 모집"으로 표시된다. 뉴스로만 존재를 아는 것, 올해 다시 열릴지
  모르는 것은 넣지 않았다. 사람이 이걸 보고 신청을 준비하므로 틀린 날짜
  한 줄이 빈 목록보다 나쁘다.

  공식 공고 URL은 되도록 채우되, 없어도 신청 기간이 확인됐으면 넣고
  카드에 "공고 확인 필요 · 문의처로 확인해 주세요"를 띄운다(현재 의성
  1건). 제3자 집계 서비스 링크는 신청 링크로 쓰지 않는다 — 공고 원문이
  아니라 재가공된 정보라 신청 근거가 될 수 없다. 넣지 못한 지역과 그
  사유도 전부 코드에 기록해 두었다(`src/data/supportPrograms.js`).

- **화면 1 설명 — 홈 지원 프로그램 티저**

## 4. 데이터 활용 (한국관광공사 OpenAPI)

총 **4개 서비스, 8개 오퍼레이션**을 사용한다. 인증키는 전부
`api/` 서버리스 함수 안에서만 쓰고 프론트엔드 번들에 넣지 않는다
(`api/_lib/tourApi.js` 한 곳에서만 `serviceKey`를 붙인다).

**호출 방식 구분** — 관광 *콘텐츠*는 전부 **실시간 호출**이며 로컬 DB에
저장하지 않는다. 반면 행정구역 코드·분류체계 코드 사전처럼 콘텐츠가 아닌
**정적 참조표**는 1회 조회해 상수로 고정했다(매 요청마다 코드 사전을 다시
받는 것은 일 1,000건 한도의 낭비이므로).

### 4-1. 실시간 호출 (사용자 요청 때마다 호출)

1. **API명**: 국문 관광정보 서비스(KorService2) — **지역기반 관광정보 조회
   `areaBasedList2`**
   - **상세설명**: 이 서비스의 중심 데이터다. `lDongRegnCd`(시도) +
     `lDongSignguCd`(시군구) + `lclsSystm1`(분류체계 대분류)로 지역별 관광
     콘텐츠 목록을 **실시간 호출**한다(`api/tour/area-based.js`).
     사용처는 셋이다. ① **둘러보기 탭**의 숙박 / 식당·카페 / 체험 프로그램 /
     주변 관광지 4개 카테고리 목록과 하위 필터 ② **체류 계획 자동 생성**의
     시간대별 후보(오전 카페 FD05, 오후 관광지 NA·HS·VE·LS + 체험 EX, 저녁
     식당 FD01~04) ③ **지역 소개·추천 게이지**의 카페·식당 건수 판정 근거.
     호출 최소화를 위해 카테고리별로 부르지 않고 분류체계 대분류로 한 번에
     받아 화면에서 나누므로 **지역 진입당 1건**으로 끝난다. 응답의 `items`가
     빈 문자열 / 단건 객체 / 배열 세 가지 모양으로 오는 것을 배열로 통일해
     처리한다. 파일럿 29곳 실측 합계는 전체 4,851건(숙박 946 · 식사류 942 ·
     카페 226)이다.

2. **API명**: 국문 관광정보 서비스(KorService2) — **공통정보 조회
   `detailCommon2`**
   - **상세설명**: 둘러보기 목록에서 장소 카드를 누르면 `contentId`로
     **실시간 호출**해 장소 상세 모달을 채운다(`api/tour/detail.js`).
     쓰는 필드는 개요(`overview`), 주소, 전화번호, 홈페이지, 대표
     이미지다. 목록 API 응답에는 `overview`가 없어서 카드에 소개 문구를
     띄울 수 없는데, 이 오퍼레이션이 그 공백을 채운다. 응답에 없는 필드는
     모달에서 칸을 숨겨 빈 라벨이 남지 않게 했다.

3. **API명**: 국문 관광정보 서비스(KorService2) — **소개정보 조회
   `detailIntro2`**
   - **상세설명**: 장소 상세 모달에서 `detailCommon2`와 **동시에 실시간
     호출**해 유형별 정보를 덧붙인다(`api/tour/detail.js`). 콘텐츠 타입
     (`contentTypeId`)마다 필드 이름이 달라서, 타입별로 뽑을 필드 목록을
     매핑해 두고(관광지 12 · 문화시설 14 · 행사 15 · 레포츠·체험 28 ·
     숙박 32 · 음식점 39, 6개 타입) 그에 맞는 것만 골라 표시한다 —
     숙박은 체크인·체크아웃·주차·객실 수, 음식점은 영업시간·휴무일·
     대표메뉴, 관광지는 이용시간·주차·쉬는 날 등이다.
     캠핑장이 분류체계로는 숙박(AC05)인데 `contentTypeId`는 레포츠(28)로
     오는 것까지 반영했다.

4. **API명**: 두루누비 정보 서비스(Durunubi) — **걷기여행길 코스 조회
   `courseList`**
   - **상세설명**: 둘러보기 탭의 **걷기 코스** 카테고리와 지역 소개
     하이라이트에 쓴다(`api/tour/duru.js`). KorService2와 같은 인증키·같은
     호출 규약이라 공용 유틸에 함께 붙였다. 코스명, 소요시간(`crsTotlRqrmHour`),
     거리, 난이도, 코스 설명을 받아 소요시간 기준 하위 필터(3시간 이내 /
     반나절 / 하루)로 나눈다. **호출 최소화**: 전국 코스가 142건이 전부라
     지역별로 부르지 않고 한 번에 다 받아 서버 메모리에 12시간 담아 두고
     `sigun`으로 걸러 주므로, 인스턴스가 살아 있는 동안 쓰는 호출은 페이지
     수만큼(현재 2건)이 전부다. 지도 경로선은 응답에 좌표가 없고 GPX 파일
     주소만 있어서, 서버가 GPX를 읽어 좌표를 뽑아 내려준다(durunubi.kr이
     CORS 헤더를 주지 않아 브라우저에서 직접 받을 수 없고, 코스당 최대
     100점으로 솎아 2.4MB를 수십 KB로 줄였다). 코스가 0건인 내륙 지역에서는
     카테고리를 빈 상태로, 지역 소개 하이라이트는 통째로 감춘다.

### 4-2. 정적 참조표 확보용 (1회 조회 후 상수화, 엔드포인트는 유지)

5. **API명**: 국문 관광정보 서비스(KorService2) — **법정동코드 조회
   `ldongCode2`**
   - **상세설명**: 파일럿 29곳의 시도 코드(`regnCd`)와 시군구 코드
     (`signguCd`)를 확보하는 데 썼다(`api/tour/ldong.js`). 이 코드가 있어야
     `areaBasedList2`로 지역별 조회를 할 수 있다. 구 `areaCode` 방식은
     폐기되어 `ldongCode2`로 직접 조회해 확인한 값이다. 행정구역 코드는
     거의 바뀌지 않는 정적 참조표라 값 자체는 `src/data/regions/`에 상수로
     고정했지만, **엔드포인트는 남겨 두었다** — 파일럿 밖 지역을 추가할 때
     `GET /api/tour/ldong?lDongRegnCd=<시도코드>`로 그때 조회해 표에 더하면
     되고 재구현이 필요 없다.

6. **API명**: 국문 관광정보 서비스(KorService2) — **분류체계코드 조회
   `lclsSystmCode2`**
   - **상세설명**: 둘러보기 하위 필터와 장소 유형 배지에 쓰는 **분류체계
     3단계 코드→이름 사전**을 받았다. 실제로 쓰는 7개 대분류(AC 숙박 ·

     필터를 누를 때 추가 호출 없이 이미 받은 목록을 걸러낼 수 있다.
     관광 콘텐츠가 아니라 콘텐츠를 분류하는 코드 사전이므로 상수로 고정했다.

     방문자 수인데, 현지인(`touDivCd=1`)을 빼고 **외지인 + 외국인**만 더해
     쓴다 — 그 지역에 사는 사람은 방문객이 아니기 때문이다. 상류 API에
     제약이 둘 있어 핸들러가 필요했다. ① `signguCd`를 넘겨도 무시되고 전국
     하루치 807건(269 시군구 × 3구분)이 통째로 오므로 서버에서 걸러야 한다
     ② 월별·연별 오퍼레이션이 없어 일별만 있다. 그래서 **29곳 × 24일

     3단계를 가른다. 예전에는
     관광 목록의 두께를 한적함 대신 썼는데, 목록이 두꺼워도 실제 방문자가
     적은 지역이 있어 판정이 어긋났다.

8. **API명**: 관광사진 정보 서비스(PhotoGalleryService1) — **키워드 검색
   `gallerySearchList1`**
   - **상세설명**: 홈 캐러셀, 지역 소개 배너·슬라이드, 마이페이지 카드에
     쓰는 **지역 대표 사진 116장(29곳 × 4장)** 을 골랐다. URL을
     `src/data/regionPhotos/`에 상수로 고정해 **런타임 호출은 0건**이다.
     그렇게 한 이유가 둘 있다. ① 홈 캐러셀·마이페이지 카드는 방문자마다

     ⓒ한국관광공사"로 출처를 표기했다.

## 6. 서비스 차별성 & 발전계획

### 차별성

**1. "여행"이 아니라 "체류"를 전제로 데이터를 다시 읽었다.**
같은 관광 데이터를 써도 묻는 질문이 다르다. 식당 목록에서 카페(FD05)를
분리해 센 것이 예다 — 워케이션 지표가 카페를 따로 세므로, 합쳐서 세면
카페가 3곳뿐인 지역에도 "식당과 카페가 넉넉해"가 붙어 카페를 과장한다.
걷기 코스 필터를 난이도가 아니라 소요시간으로 만든 것도, 며칠~한 달
머무는 사람이 실제로 알아야 하는 건 "이 코스가 내 반나절을 가져가는가"
이기 때문이다(난이도별 소요시간 중앙값은 270분으로 모두 같았다).

**2. 화면의 모든 판정에 측정한 근거가 있다.**
생활 여건 게이지, 지역 소개 문구, 한적함, 교통 접근, 추천 정렬을 전부
실측값으로 계산한다. 개발 과정에서 지역명 해시로 점수를 만드는 코드를
전부 걷어냈다 — 그 방식은 카페가 1곳인 지역에 "코워킹 공간이 있어요"를
붙이고, 카페가 15곳인 지역에 "몇 곳 있어요"를 붙였다. 지역 소개와 추천
결과가 **같은 함수**를 부르게 해 두 화면이 어긋날 수 없게 만든 것도 같은
이유다. 반대로 **말하지 않을 것**도 정했다: 마트·병원·코워킹 공간은
관광공사 목록에 없는 정보이므로 언급하지 않는다.

**3. 사실 검증을 데이터 수집 규칙으로 못박았다.**
지원 프로그램은 공식 공고에서 신청 기간까지 확인한 것만 넣는다. 개발
중간에 디자인에서 옮겨 온 목업 12건을 전부 지웠고(실재하지 않는 사업명,
인구감소지역이 아닌 지역이 섞여 있었다), 넣지 못한 지역과 그 사유를 코드에
남겼다. 정부 공식 창구라도 마을별 내용을 서버에서 주지 않아 링크를 걸면
방문자가 엉뚱한 마을을 보게 되는 경우는 제외했다. 심사에 보이지 않는
부분이지만, 사람이 이걸 보고 신청을 준비하므로 틀린 날짜 한 줄이 빈
목록보다 나쁘다고 판단했다.

**4. 일 1,000건 호출 한도 안에서 동작하도록 설계했다.**
카테고리 5개를 대분류 1회 호출로 처리해 지역 진입당 1건, 걷기 코스는
전국 142건을 서버에 12시간 캐시해 방문자 수와 무관하게 페이지 수만큼,
사진·행정구역 코드·분류체계 사전·방문자수는 정적 참조값으로 고정해 0건.
그러면서 관광 **콘텐츠**는 로컬에 저장하지 않고 실시간 호출을 유지했다.

**5. 계획을 결과물로 가지고 나갈 수 있다.**
자동 생성 일정이 난수를 쓰지 않는 순수 계산이라 저장한 계획을 다시 열어도
같은 일정이 나오고, 최종 계획을 엑셀 2시트(일정 / 비용 근거)와 인쇄로
내보낼 수 있다. 화면에서 끝나지 않고 실제 준비에 쓰이도록 했다.

### 발전계획

**1단계 — 추천 정렬을 데이터로 교체 (구조는 이미 준비됨)**
지금 남은 유일한 목업은 추천 "순위"다. 고른 라이프스타일이 주분류인 지역을
앞에 두는 정렬로 대신하고 있는데, 방문자수·수요강도·재방문율 데이터를
결합한 점수로 바꿀 계획이다. 교체 지점은 `services/regionRecommend.js`의
`getRecommendations()` 하나이고 시그니처만 유지하면 화면은 손대지 않는다.
서버리스 함수 자리도 `api/region/recommend.js`로 비워 두었다.

**2단계 — 지원 프로그램 자동 수집과 마감 알림**
현재 11건은 사람이 공고를 열어 확인한 것이다. 지자체 고시공고 게시판의
RSS·전자민원 목록을 주기적으로 읽어 후보를 모으고 사람이 확인만 하는
구조로 바꾸면 수집 비용이 크게 줄어든다. 데이터 배열을
`api/support/programs.js`가 돌려주는 형태로 바꿔도 필드 이름만 유지하면
계산 로직은 그대로다. 그 위에 **마감 임박 알림**(카드 하단에 자리는 이미
있다)과 **신청 방법**(온라인 / 방문 / 이메일)·**선정 방법**(선착순 / 심사)
필드를 더해, 놓치기 쉬운 짧은 신청 기간을 실제로 챙겨 주려 한다.

**3단계 — 대상 지역 확대**
현재 29곳은 3개 광역의 인구감소지역이다. 지역을 추가하는 작업이
`api/tour/ldong.js`로 법정동 코드를 조회해 광역별 파일에 한 줄 더하는
것으로 끝나도록 만들어 두었다. 전국 89개 인구감소지역 전체로 넓히는 것이
목표이고, 그때는 광역 필터를 3개에서 전국 시도로 확장한다.

**4단계 — 체류 준비에 실제로 필요한 정보 보강**
관광공사 API에 없어서 지금 말하지 못하는 것들이다. 체험 프로그램의
소요시간·가격, 숙소 실시간 예약 가능 여부와 장기 체류 할인, 마트·병원·
코워킹 공간 같은 생활 인프라. 지자체 공공데이터와 민간 API를 붙여 채우려
한다. 숙소는 `contentId`가 이미 있으므로 예약 링크를 고정 URL에서 장소별
링크로 바꾸는 것이 먼저다.

**5단계 — 지역·이용자 양쪽에 쓰이는 데이터로**
계획 단계에서 모인 익명 집계(어느 지역·기간·테마가 많이 선택되는가,
어느 지원 프로그램에 관심이 쏠리는가)는 지자체가 체류 인구 정책을 세울 때
쓸 수 있는 정보다. 개인정보를 담지 않는 집계 리포트 형태로 지자체에
제공하는 것을 검토한다.

**촬영 시 주의**
- 걷기 코스 경로선이 보이는 지역으로 잡을 것: **강원 고성(12코스)**,
  충남 태안(6코스). 내륙 지역은 코스가 0건이라 카테고리가 빈 상태로 나온다.
- 지원 프로그램 카드는 **모집 상태가 다양하게** 보이는 순간이 좋다.
  기준일에 따라 상태가 자동으로 바뀌므로 캡처 직전에 화면을 확인할 것.
- 지도가 나오는 화면은 `VITE_KAKAO_MAP_KEY`가 설정되고 **촬영 환경 도메인이
  Kakao Developers에 등록된 상태**여야 한다. 안 되면 목업 셸이 찍힌다.
- 로그인 상태 캡처가 필요하면 `VITE_GOOGLE_CLIENT_ID`가 필요하다.
