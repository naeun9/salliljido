# 03. 한국관광공사 TourAPI(KorService2) 실연동 1단계 검증

목표: 서버리스 함수 하나(`api/tour/area-based.js`)로 실제 호출이 되는지
검증하는 것까지만. 화면 컴포넌트는 손대지 않았다.

## 0. 사전 확인

- `.env.local`의 `TOUR_API_KEY`는 공공데이터포털 **Decoding 키**(퍼센트 인코딩
  안 된 원문 값)다.
- **이중 인코딩 주의**: `URLSearchParams`에 원문 키를 그대로 넣으면
  `.toString()` 시점에 정확히 한 번만 퍼센트 인코딩된다. 이 키를 다른 곳에서
  먼저 `encodeURIComponent()`로 인코딩한 뒤 넘기면 이중 인코딩(`+`가 `%2B`가
  아니라 `%252B`가 되는 식)이 되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(30)
  같은 인증 오류가 난다. → `api/_lib/tourApi.js` 한 곳에서만 `serviceKey`를
  `URLSearchParams`에 원문 그대로 넣고, 그 밖에서는 절대 손대지 않도록
  했다.
- 이 문서 어디에도 키 값 자체는 적지 않았다(콘솔 출력에도 찍은 적 없음).

## 1. 구현한 파일

- **`api/_lib/tourApi.js`** — TourAPI 공용 호출 유틸. `callTourApi(operation, params)`가
  `serviceKey`/`MobileOS=WEB`/`MobileApp=salliljido`/`_type=json`을 붙여
  호출하고, 성공/실패를 `{ ok, body }` 또는 `{ ok:false, errorCode, message }`로
  통일해 돌려준다. `normalizeItems(body)`는 `items`가 `""`(빈 문자열) /
  `{item: {...}}`(단건) / `{item: [...]}`(복수) 세 가지로 오는 걸 항상
  배열로 통일한다. 파일명이 `_lib`인 이유: Vercel은 `api/` 아래 밑줄로
  시작하는 폴더를 라우트로 취급하지 않는다(공식 컨벤션) — 진짜
  엔드포인트가 아니라 공용 코드임을 표시.
- **`api/tour/ldong.js`** — `ldongCode2` 프록시. `lDongRegnCd` 없이 호출하면
  시도 목록, 넘기면 그 시도의 시군구 목록을 돌려준다. 아래 §2 법정동 코드
  조회에 실제로 이걸로 조회했다.
- **`api/tour/area-based.js`** — `areaBasedList2` 프록시. 요청 지시에 있는
  파라미터(`lDongRegnCd`/`lDongSignguCd`/`contentTypeId`/`lclsSystm1~3`/
  `numOfRows`/`pageNo`/`arrange`)를 그대로 받아 전달하고, 응답의
  `items`를 정규화해서 화면에서 바로 쓰기 좋은 필드만 골라 반환한다
  (§4 참고).
- **`src/data/regionCodes.js`** — 파일럿 3개 시/도(강원·충남·경북) 15개
  시/군의 법정동 코드 상수표(§2).

## 2. 법정동 코드 확보 — 어느 쪽을 골랐나

`api/tour/ldong.js`(재사용 가능한 엔드포인트)를 **먼저 만들고**, 그걸로 한
번 조회해서 나온 값을 `src/data/regionCodes.js`에 **상수로 저장**하는
방식으로 했다 — 양자택일이 아니라 둘 다:

- 법정동 코드는 행정구역 코드라 거의 안 바뀌는 정적 참조표다. 매 요청마다
  다시 조회할 이유가 없어서(그리고 CLAUDE.md의 "실시간 호출 유지"는 관광
  *콘텐츠*에 해당하는 규칙이지, 이걸 부르기 위한 좌표값에는 해당하지
  않는다고 판단했다) 값 자체는 상수로 굳혔다.
- 대신 `ldong.js` 엔드포인트는 남겨뒀다 — 나중에 파일럿 3개 시/도 밖의
  지역이 추가되면 `GET /api/tour/ldong?lDongRegnCd=<시도코드>`로 그때

## 3. 로컬 검증 방법

`vercel dev`를 시도했으나 이 환경에서는 쓸 수 없었다:

- Vercel 계정 로그인이 안 돼 있고, 로그인 플로우를 시작하려는 순간
  경로에 포함된 한글(`바탕 화면` 등) 때문에 `Cannot convert argument to
  a ByteString` 에러로 그 자리에서 죽는다.

그래서 "동등한 방법"으로, `api/tour/*.js`가 내보내는 `handler(req, res)`를
Node에서 직접 import해서 mock `req.query`/`res.status().json()`으로
호출하는 스크립트로 검증했다. **실제 배포되는 파일을 그대로 실행**하는
것이라 프로덕션과 코드 경로가 동일하다(별도 재구현 없음). 검증 스크립트는
스크래치패드에만 뒀고 저장소에는 남기지 않았다.

### 소도시에서 부족한 카테고리

- **숙박(32)이 가장 취약하다.** 서천·홍성 2건, 청양·의성 1건 — "며칠~한
  달 살기"의 핵심 데이터인데 소도시일수록 사실상 못 쓸 수준이다. 반면
  태안(91)·안동(55)·속초(39)는 충분하다. 인구감소지역이라는 서비스
  타깃 자체가 구조적으로 숙박 데이터가 얇은 지역과 겹친다는 뜻이라,
  다음 단계에서 이 부족분을 어떻게 보완할지(예: 지자체 숙소 안내와
  결합, 최소 건수 미달 시 UI에서 "정보가 적어요" 안내) 고민이 필요하다.
- **문화시설(14)도 전반적으로 얇다.** 안동(26)만 예외고 나머지는
  3~16건. 인구감소지역의 특성상 예상 가능한 결과.
- **레포츠(28)는 지역 편차가 크다.** 양양 50 vs 의성 4 — 해안/설악산
  인접 지역(양양·인제·태안)은 액티비티가 많고 내륙 소도시(의성·홍성)는
  거의 없다.
- 관광지(12)·음식점(39)은 15개 지역 전부 두 자릿수 이상으로 상대적으로
  탄탄하다.

### 분류체계(lclsSystm) 필터 테스트

`lclsSystm1=EX`(체험관광), `lclsSystm1=FD`(음식)를 태안/청양/의성에
걸어봤다:

| 지역 | EX(체험관광) | FD(음식) | 참고: contentTypeId=39(음식점) |
|---|---:|---:|---:|
| 태안 | 14 | 61 | 61 |
| 청양 | 14 | 10 | 10 |
| 의성 | 4 | 9 | 9 |

발견한 것:
- **`lclsSystm1=FD`와 `contentTypeId=39`(음식점)가 세 지역 모두 정확히
  같은 건수를 돌려준다.** 현재 데이터에서는 FD 분류가 음식점
  콘텐츠타입과 사실상 1:1로 겹친다는 뜻 — 굳이 둘을 같이 걸 필요가
  없어 보인다(다만 전국 단위로 표본을 더 넓혀봐야 완전히 확신할 수
  있다).
- **`lclsSystm1=EX`는 `contentTypeId=12`(관광지)의 부분집합이다.**
  태안에서 `EX+contentTypeId=12`를 같이 걸면 14건(EX 단독과 동일),
  `EX+contentTypeId=28`(레포츠)를 걸면 0건 — 체험관광 항목은 전부
  "관광지" 콘텐츠타입 안에 들어있고 레포츠 쪽엔 없다.
- NODATA 조합(경북/의성 + 숙박 + EX)을 일부러 걸어봤더니 에러가 아니라
  `{ items: [], totalCount: 0 }`로 정상 응답 — `callTourApi`의 NODATA
  처리(§5)가 의도대로 동작함을 확인했다.

## 5. 에러 처리 검증

일부러 잘못된 서비스키로 호출해서 실제 에러 응답 모양을 확인했다(둘 다
같은 종류의 에러인데 형태가 다르게 온다는 걸 발견했다):

- `ldongCode2`를 무효한 키로 호출 → **JSON**으로 왔다:
  `{"OpenAPI_ServiceResponse":{"cmmMsgHeader":{"errMsg":"SERVICE_KEY_IS_NOT_REGISTERED_ERROR","returnAuthMsg":"등록되지않은 서비스키","returnReasonCode":"30"}}}`
  — `_type=json`을 요청했는데도 **정상 응답과는 다른 모양**
  (`response.header`가 아니라 `OpenAPI_ServiceResponse.cmmMsgHeader`)이라
  처음엔 `callTourApi`가 이걸 못 알아보고 "응답에 header가 없습니다"라는
  뭉뚱그린 메시지를 냈다 — 이 형태를 별도로 처리하도록 고쳤다(§6).
- 문서·커뮤니티에는 이런 게이트웨이 레벨 에러가 XML로 온다는 사례도
  많아서, XML로 오는 경우(`<OpenAPI_ServiceResponse><cmmMsgHeader>...`)에
  대한 처리도 같이 남겨뒀다. 이번 검증에서는 XML로 오는 케이스를 실제로
  재현하지는 못했다(우리 방화벽/네트워크 조건에서는 이 무효 키 시나리오가
  항상 JSON으로 왔다) — 이후 실제 운영 중 XML로 오는 에러를 만나면 이
  분기가 이미 있으니 그대로 잡힌다.
- 두 형태 모두 `returnReasonCode`를 꺼내 아래 표로 매핑한다(공공데이터포털
  공통 에러코드):

  | 코드 | 이름 | 의미 |
  |---|---|---|
  | 1 | APPLICATION_ERROR | 어플리케이션 에러 |
  | 2 | DB_ERROR | 데이터베이스 에러 |
  | 3 | NODATA_ERROR | 데이터 없음 (→ 정상 빈 결과로 처리) |
  | 4 | HTTP_ERROR | HTTP 에러 |
  | 5 | SERVICETIMEOUT_ERROR | 서비스 연결 실패 |
  | 10 | INVALID_REQUEST_PARAMETER_ERROR | 잘못된 요청 파라미터 |
  | 11 | NO_MANDATORY_REQUEST_PARAMETERS_ERROR | 필수 파라미터 누락 |
  | 12 | NO_OPENAPI_SERVICE_ERROR | 없는/폐기된 서비스 |
  | 20 | SERVICE_ACCESS_DENIED_ERROR | 서비스 접근 거부 |
  | 21 | TEMPORARILY_DISABLE_THE_SERVICEKEY_ERROR | 일시 중지된 키 |
  | 22 | LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR | 요청 한도 초과 |
  | 30 | SERVICE_KEY_IS_NOT_REGISTERED_ERROR | 미등록 키 |
  | 31 | DEADLINE_HAS_EXPIRED_ERROR | 기한 만료 |
  | 32 | UNREGISTERED_IP_ERROR | 미등록 IP |
  | 33 | UNSIGNED_CALL_ERROR | 서명되지 않은 호출 |
  | 99 | UNKNOWN_ERROR | 기타 |

- 무효 키로 재현 테스트 결과: `{"ok":false,"errorCode":"30","message":"SERVICE_KEY_IS_NOT_REGISTERED_ERROR — 등록되지 않은 서비스키"}` —
  의도한 그대로 나왔다.

## 6. 이번에 발견한 제약·주의점 (자체 발견, 수정 완료)

- **`callTourApi`가 게이트웨이 에러의 JSON 모양을 놓치던 버그.** 위 §5에서
  설명한 대로, 무효 키 응답이 XML이 아니라 `OpenAPI_ServiceResponse.
  cmmMsgHeader` 모양의 **JSON**으로 왔는데 처음 짠 코드는 XML만 따로
  걸러내고 나머지는 전부 `response.header` 모양이라고 가정했다. 실제
  호출로 검증하다가 바로 드러나서 그 자리에서 고쳤다 — 이런 종류의
  버그는 무효 키를 실제로 던져보지 않으면 절대 못 잡는다.
- **`_type=json`을 요청해도 100% JSON이 보장되지 않는다.** 정상 응답과
  에러 응답의 최상위 모양 자체가 다르다(`response.header` vs
  `OpenAPI_ServiceResponse.cmmMsgHeader`, 게다가 후자는 XML로도 올 수
  있음). 프록시는 이 셋을 전부 구분해서 처리해야 한다 — 처리했다.
- **응답에서 화면에서 못 쓰는 필드가 실제로 있었다.** `areacode`,
  `sigungucode`, `cat1`/`cat2`/`cat3`(레거시 관광지 분류)는 최근 등록된
  항목일수록 빈 문자열로 오는 경우가 많았다(태안 관광지 5건 표본 중
  4건이 `areacode:""`). 대신 `lDongRegnCd`/`lDongSignguCd`,
  `lclsSystm1~3`은 항상 채워져 있었다 — 지시에서 "areaCode 방식은
  폐기됐다"고 한 것과 정확히 일치하는 결과다. `api/tour/area-based.js`의
  `normalizeItem()`은 이 관찰에 따라 레거시 필드를 빼고
  `lDongRegnCd`/`lDongSignguCd`/`lclsSystm1~3` 중심으로 정리했다.
- **이미지가 없는 항목도 있다.** `firstimage`가 비어 있고
  `firstimage2`만 있거나 둘 다 빈 항목이 섞여 있다(표본에선 5건 다
  있었지만 전수는 아님) — 화면 붙일 때 이미지 placeholder 처리가
  필요하다.
- **`tel`(전화번호)은 자주 비어 있다.** 위 표본 5건 중 5건 다
  `tel:""` — 화면에서 "전화 문의" 같은 UI를 만든다면 빈 값 처리가
  필수.
- **요청 한도.** 이번 검증(약 85회 호출)은 문제없이 전부 성공했다 —
  키 등급별 일일 한도(공공데이터포털 기본 승인은 보통 1,000회/일)를
  넘지 않는 선에서 여유 있게 끝났다. 다음 단계에서 화면이 실제로 여러
  카테고리를 동시에 부르게 되면(예: 둘러보기 탭이 숙박+체험+관광지+
  식당카페 4번을 한 번에 부름) 한도 소진 속도를 다시 가늠해봐야 한다.

## 7. 응답 필드 — 화면에서 쓸 수 있는 것 / 없는 것

| 필드 | 쓸 수 있음? | 비고 |
|---|---|---|
| `contentid` / `contenttypeid` | ✅ | 상세조회(`api/tour/detail.js`, 다음 단계)에 필요한 키 |

# 2단계: 숙박 데이터 보강 (고캠핑 통합)

## 9. 고캠핑(GoCamping) 연동

### 9-1. 구현한 것

- **`api/tour/camping.js`** — GoCamping `basedList` 프록시. `doNm`/
  `sigunguNm`을 받아 그 지역 캠핑장만 걸러 돌려준다.
- **`api/_lib/tourApi.js` 리팩터** — `callTourApi`(KorService2 전용)였던
  걸 내부적으로 `callOpenApi(baseUrl, ...)`로 일반화하고,
  `callGoCampingApi`를 새로 노출했다. 응답 파싱 로직(에러 모양 구분)도
  공유한다 — 자세한 이유는 아래 9-2 참고.

### 9-2. GoCamping API 실제 호출해보고 발견한 제약

KorService2와는 다른 API 제품이라 예상과 다르게 동작하는 부분이 여럿
있었다 — 전부 실제로 호출해서 확인한 것이다:

- **`doNm`/`sigunguNm`/`areaCode` 전부 `basedList`의 입력 파라미터로
  안 받아준다.** 셋 다 시도해봤고 전부
  `INVALID_REQUEST_PARAMETER_ERROR(파라미터명)`으로 거부당했다. 즉
  KorService2와 달리 **행정구역 기준으로 서버에서 걸러주는 방법이
  없다.**
- **`searchList`(키워드 검색)로 대신해보니 부정확했다.** `keyword=태안`은
  총 11건만 돌아왔는데, 실제로는 이름에 "태안"이 없는 진짜 태안군
  캠핑장(예: "구름포해수욕장카라반")은 안 잡히고, 반대로 이름에
  "태안"이 들어간 서산시 캠핑장("...충남서산태안점")은 잘못 포함됐다 —
  이름 텍스트 매칭이라 지역 필터로 못 쓴다.
- **그래서 택한 방식**: `doNm`/`sigunguNm`이 주어지면 `basedList`를
  `numOfRows=9999`로 한 번에 불러(전국 약 3,096건, 응답 약 5.6MB, 약
  2초) 응답에 실제로 들어있는 `doNm`/`sigunguNm` **출력** 필드로 여기서
  직접 거른다. `numOfRows`를 얼마로 넘기든 호출 자체는 1번이라
  공공데이터포털의 "건수 기준" 일일 한도에는 영향이 없다(§11에서 더
  설명).
- **응답 최상위 모양이 KorService2와도, 같은 GoCamping 안에서도
  다르다.** 파라미터 에러(`doNm` 거부 등)는 `{responseTime, resultCode,
  resultMsg}`처럼 **껍데기 없이** 최상위에 바로 온다 — KorService2의
  `response.header`도, 게이트웨이 에러의 `OpenAPI_ServiceResponse.
  cmmMsgHeader`도 아닌 **세 번째 모양**. `api/_lib/tourApi.js`의
  `parseOpenApiResponse()`가 이 세 가지(+XML 게이트웨이 에러까지 네
  가지)를 전부 구분하도록 고쳤다.
- **레거시 도명이 섞여 있다(자체 발견, 수정 완료).** 2023년 개편으로
  "강원도"→"강원특별자치도", "전라북도"→"전북특별자치도"로 이름이
  바뀌었는데, GoCamping 데이터는 최신 도명과 옛 도명이 섞여 있다.
  처음에 "강원특별자치도"로만 매칭했더니 **속초시 캠핑장이 0건**으로
  나와서 이상해 `addr1`로 직접 뒤져봤더니 3건 다 `doNm:"강원도"`로
  등록돼 있었다 — 신규 도명만 비교했으면 조용히 다 놓쳤을 것이다.
  `camping.js`에 `DO_NM_ALIASES`로 두 도명을 다 인정하도록 고쳤다(양양군
  25→53건, 정선군 4→17건, 인제군 7→39건, 삼척시 8→16건, 속초시 0→3건 —
  강원 5개 시/군 전부 크게 늘었다).
- **필드 공백 오염도 있다.** `"충청남도 "`처럼 앞뒤 공백이 낀 값이
  실제로 있어(위 alias 문제와 별개로) 비교 전에 `trim()`한다.

## 10. 하위 필터 구조 검토 — 캠핑/야영장 유형 추가 가능한가

design 원본(`subDefs`, `salliljido.html` 내부)의 숙박 하위 필터는 고정
리스트다:

```
"숙박": { list: ["호텔", "펜션·민박", "콘도", "한옥스테이", "농어촌민박"], src: stays }
```

각 숙박 항목은 `sub` 필드가 이 5개 중 하나와 정확히 일치해야 해당 칩을
눌렀을 때 걸러진다(`src/services/exploreListings.js`의 `STAYS` 배열,
design을 그대로 옮긴 상태).

**검토 결과: 구조를 안 건드리고 추가할 수 있다.** `list`는 그냥 문자열
배열이라 끝에 항목을 하나 더 넣는 것만으로는 기존 5개 칩의 동작·표시
방식·스타일 어느 것도 바꾸지 않는다(추가일 뿐 변경이 아님). 실제로
붙이려면(다음 단계, 화면 연동 시):

1. `list`에 `"캠핑·야영장"` 한 항목 추가.
2. `camping.js`가 돌려주는 `induty`(일반야영장/자동차야영장/카라반 등,
   §9-1 정규화 필드 참고)를 이 하나의 `sub` 값으로 매핑 — 세부 업종별로
   칩을 더 쪼갤 수도 있지만(예: "글램핑" 별도), 그건 원본에 없는 칩을
   새로 만드는 것이라 이번 검토 범위(원본 구조 유지)를 벗어난다. 굳이
   나누고 싶다면 그건 화면 연동 단계에서 별도로 다시 여쭤볼 것.
3. `STAYS`(또는 그걸 대체할 실제 API 결과 배열)에 캠핑 항목을 합칠 때
   `sub: "캠핑·야영장"`을 붙여서 넣으면 기존 필터링 로직(`x.sub ===
   selectedSub`)이 그대로 동작한다 — 필터링 코드 자체를 고칠 필요가
   없다.

이번 단계에서는 검토만 했고 `exploreListings.js`나 `subDefs` 어느 쪽도
건드리지 않았다(지시대로 화면/데이터 서비스 레이어는 다음 단계).

## 11. 호출 최적화 — 다음 단계(화면 연동)를 위한 지침

아직 화면이 이 엔드포인트들을 부르지 않으므로 "고친" 건 없고, 다음
단계에서 그대로 따라야 할 지침만 정리한다.

- **`lclsSystm1=FD`와 `contentTypeId=39`(음식점)를 같이 쓰지 말 것.**
  §4에서 확인한 대로 셋 지역 다 완전히 같은 결과를 줬다. 식당·카페
  카테고리는 `contentTypeId=39` 하나만 쓰면 된다.
- **체험 프로그램 카테고리는 `lclsSystm1=EX` 하나만 쓸 것.**
  `contentTypeId=12`를 같이 붙여도(§4에서 확인) 결과는 똑같다 —
  같은 API 호출 1번이라 파라미터 개수 자체가 quota에 영향을 주진
  않지만, `lclsSystm1=EX`만 쓰는 쪽이 "체험관광 전체"라는 의도를 더
  분명히 드러내고 나중에 EX가 다른 콘텐츠타입으로도 확장되면(현재는
  관광지의 부분집합이지만 원본 API 쪽 정책이 바뀔 수 있음)
  `contentTypeId=12`가 오히려 결과를 좁혀버리는 실수를 막는다.
- **숙박 카테고리는 원래부터 호출 2번이 필요하다.** `contentTypeId=32`
  (일반 숙박, `area-based.js`)와 `camping.js`(캠핑)는 서로 다른 API
  제품이라 하나로 합쳐 부를 수 없다 — 화면에서 숙박 탭을 열 때마다
  2번 부르는 게 최소치다. 그 이상(예: 재검색할 때마다 다시 부르는 것)은
  피할 것.
- **`camping.js`는 지역을 넘기면 매번 전국 데이터(약 5.6MB)를 받아
  거른다(§9-2).** 호출 횟수(quota) 기준으로는 여전히 1번이라 문제
  없지만, 응답 시간·대역폭은 다른 엔드포인트보다 눈에 띄게 크다 —
  화면에서 로딩 상태를 그에 맞게(다른 카테고리보다 느릴 수 있다는 전제
  로) 설계할 것.
- **일일 1,000건 한도는 KorService2와 GoCamping이 별도 상품이라 각자
  따로 셀 가능성이 높다**(공공데이터포털은 활용신청을 상품 단위로
  받는다). 확인하려면 공공데이터포털 마이페이지의 "활용현황"에서 두
  상품(관광정보서비스/고캠핑정보서비스)의 카운터가 따로 잡히는지
  보면 된다 — 이번 검증 코드에서는 접근할 수 없어 가정으로 남긴다.
  둘러보기 탭 전체(관광지+체험+식당카페+숙박2번) 기준 한 번의 화면
  진입에 약 5회 호출이 예상된다.
- 이번 단계에서 실제로 부른 횟수: 1단계(§4) 약 85회 + 2단계(camping
  관련) 약 20회 남짓 — 전부 성공, 한도 근처에도 못 갔다.

# 3단계: 둘러보기 탭 실데이터 연동

## 12. 카테고리 4개를 지역 조회 1번으로 해결 (호출 최소화)

2단계까지의 계획은 카테고리마다 따로 부르는 것이었다(숙박 2번 + 식당 +
체험 + 관광지 = 5번). 그런데 `areaBasedList2`를 **contentTypeId도
lclsSystm1도 없이** 지역 코드만 주고 부르면 그 지역 전체가 한 번에 오고,
응답의 `lclsSystm1`로 네 카테고리를 나눌 수 있다는 걸 확인했다.

| 지역 | totalCount | 응답 크기 | 소요 | 숙박 | 식당·카페 | 체험 | 주변 관광지 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 태안 | 360 | 209KB | 317ms | 131 | 61 | 14 | 142 |
| 속초 | 270 | 156KB | 188ms | 37 | 108 | 11 | 94 |
| 안동 | 257 | 149KB | 289ms | 59 | 27 | 11 | 126 |
| 양양 | 244 | 144KB | 183ms | 51 | 56 | 12 | 118 |
| 의성 | 62 | 37KB | 114ms | 3 | 9 | 4 | 44 |
| 청양 | 56 | 33KB | 138ms | 6 | 10 | 14 | 22 |

파일럿 15개 시/군 중 가장 큰 곳이 270건이라 `numOfRows=500` 한 번이면
잘림 없이 다 받는다(위 6개 지역 모두 `totalCount === 받은 건수` 확인).

**결과: 화면 진입 1회당 API 호출 1번.** 카테고리·하위 필터 전환은 추가
호출이 전혀 없다(Playwright로 4개 카테고리를 모두 돌아본 뒤에도 호출
1건인 것 확인). 일 1,000건 한도 기준으로 하루 1,000번의 지역 열람이
가능하다는 뜻이라 2단계 예상(진입당 5회)보다 5배 여유가 생겼다.

세션 캐시는 `services/exploreListings.js`의 모듈 스코프 `Map` 하나뿐이다
(지역 코드 → 응답 Promise). 파일·DB에 쓰지 않으므로 새로고침하면 비고
그때 다시 실시간으로 받아온다 — CLAUDE.md의 실시간 호출 원칙을 지킨다.

### 숙박: `lclsSystm1=AC` 한 번이면 캠핑까지 포함된다

2단계에서는 숙박을 "일반 숙박(contentTypeId=32) + 고캠핑(GoCamping)"으로
합치기로 했는데, 이번에 분류체계로 조회해보니 **캠핑장이 이미
`lclsSystm1=AC`(AC05 캠핑) 안에 들어있다**. contentTypeId로만 보면
캠핑장이 32가 아니라 **28(레포츠)** 에 등록돼 있어서 안 보였던 것이다.

| 지역 | 일반 숙박(32) | AC 전체(캠핑 포함) | 그중 캠핑(AC05) | 참고: GoCamping |
|---|---:|---:|---:|---:|
| 태안 | 91 | 131 | 44 | 60 |
| 양양 | 28 | 51 | 25 | 53 |
| 인제 | 14 | 44 | 30 | 39 |
| 서천 | 2 | 13 | 11 | 17 |
| 홍성 | 2 | 7 | 5 | 11 |
| 청양 | 1 | 6 | 5 | 5 |
| 의성 | 1 | 3 | 2 | 5 |
| 속초 | 39 | 37 | 3 | 3 |

**`lclsSystm1=AC` 하나로도 15개 지역 전부 3건 이상**이라 2단계에서 세운
"3건 미만 지역 없음" 기준을 그대로 만족한다. 그래서 둘러보기 탭은
GoCamping을 부르지 않고 지역 조회 1번에 포함된 AC 항목만 쓴다.

트레이드오프(판단이 필요하면 알려줄 것):
- **AC 방식(현재 적용)**: 호출 0회 추가(지역 조회에 이미 포함), 응답
  필드가 다른 카테고리와 완전히 동일, 좌표계도 동일.
- **GoCamping 방식**: 캠핑장이 지역에 따라 최대 35% 더 많지만(태안
  44→60), 전국 5.6MB를 받아 걸러야 하고 필드 모양이 달라 별도 정규화가
  필요하다. `api/tour/camping.js`는 지우지 않고 남겨뒀으니, 캠핑 데이터를
  최대로 늘리고 싶으면 그때 합치면 된다.

## 13. 하위 필터는 분류체계와 거의 1:1로 맞는다

design의 하위 필터 라벨이 관광공사 분류체계에서 그대로 나온 것으로
보인다. 실제 코드표(`lclsSystmCode2`)와 맞춰보니:

| design 카테고리 | design 하위 필터 | 대응 코드 | 일치도 |
|---|---|---|---|
| 식당·카페 | 한식/외국식/간이음식/카페/주점 | FD01~FD05 | **완전 일치** |
| 체험 프로그램 | 전통체험/공예체험/농촌·어촌체험/템플스테이/웰니스/산업관광 | EX01~EX06 | **완전 일치**(템플스테이=EX04 산사체험) |
| 주변 관광지 | 자연/역사/문화/레저스포츠 | NA/HS/VE/LS | **완전 일치**(대분류 그대로) |
| 숙박 | 호텔/펜션·민박/콘도/한옥스테이/농어촌민박 | AC01/AC030100·AC030400/AC02/AC030200/AC030300 | 일치(3단계까지 내려가면) |

즉 **design의 필터 구조를 하나도 바꾸지 않고** 코드 매핑만으로 붙일 수
있었다. 숙박에만 `캠핑·야영장`(AC05) 하나를 끝에 추가했다(요청사항 1).

매핑 표는 `src/data/tourCategories.js`의 `SUB_FILTER_CODES`에 있다.

### 어느 필터에도 안 걸리는 항목

`AC04`(모텔), `AC06`(호스텔), `EX07`(기타체험)은 design에 대응 칩이 없다.
이 항목들은 **하위 필터를 아무것도 안 골랐을 때만** 목록에 나온다.
design에 없는 칩을 새로 만들지 않기 위한 선택이다(예: 태안 숙박 131건 중
모텔 8 + 호스텔 2 = 10건이 여기 해당).

### 관광지에서 체험(EX)을 빼야 한다 — 판단 결과

`contentTypeId=12`(관광지)에는 체험관광(EX)이 섞여 있다(태안 123건 중
EX가 14건). 그대로 두면 체험 프로그램 탭과 **같은 항목이 두 카테고리에
중복 노출**된다. 그래서 주변 관광지는 `NA/HS/VE/LS`만 담도록 EX를
제외했다(`CATEGORY_LCLS1`). 반대로 design의 `레저스포츠` 필터는
contentTypeId=12에 아예 없고 28에 있는데, 분류체계(LS)로 나누면 이것도
자연히 해결된다 — contentTypeId 대신 lclsSystm1으로 가른 또 하나의 이유다.

## 14. 실데이터에서 비는 필드 (빈 값 처리)

태안 전체 360건 기준으로 실제 측정한 값이다.

| 필드 | 상태 | 화면 처리 |
|---|---|---|
| `title`, `addr1`, `mapx`/`mapy`, `lclsSystm1~3` | 100% 채워짐 | 그대로 사용 |
| `firstimage` | **숙박 46%(42/91), 식당 23%, 관광지 4%가 없음** | design 원본의 스와치 + `image` 라벨 플레이스홀더를 그대로 사용 |
| `tel` | **전 카테고리 100% 비어 있음**(360/360) | 카드에서 안 씀 (design에도 전화번호 자리가 없었다) |
| `addr2` | 106/123이 빈 값 | `addr1`과 공백으로 이어 붙이되 빈 값이면 무시 |
| `overview`(소개 문구) | **areaBasedList2에 아예 없음** | 아래 참고 |
| 체험 소요시간·가격 | **API에 없는 개념** | 아래 참고 |

### 소개 문구가 없는 문제

design의 카드는 `desc`/`note`/`location`에 짧은 소개 문구를 넣었는데
(예: "물때에 맞춰 조개를 캐고 갯벌 생물을 관찰합니다"), 목록 API에는
이런 문구가 없다. `detailCommon2`에는 `overview`가 있지만 **항목 1개당
1회 호출**이라 목록 화면에서는 못 쓴다(태안 한 지역만 360회 → 일일 한도
3분의 1 소진).

그래서 그 자리에 **주소**를 넣었다. 배지에는 분류체계 3단계 이름을
짧게 줄여 쓴다(예: `AC030100` → "펜션", `NA010100` → "산"). 카드가
"이름 + 유형 배지 + 한 줄 정보" 구조라 주소가 그 자리에 자연스럽게 들어간다.

### 체험 소요시간·가격이 없는 문제

design의 체험 카드는 소요시간("2시간")과 가격("1만 5천 원")을 함께
보여주는데, **관광공사 API에는 두 값이 아예 없다**(detailCommon2에도
없다 — 유료/무료 여부조차 없음). 지금은 두 값이 모두 비면 그 줄을 통째로
감춘다. 빈 span 두 개만 남기면 간격만 벌어져서다.

이건 다음 단계에 영향이 크다 — §15 참고.

## 15. 다음 화면 연동 시 주의할 점

- **⚠️ 담은 체험이 체류 계획·예상 비용 탭으로 넘어가지 않는다.**
  둘러보기 탭이 실제 `contentId`(예: `"2629105"`)를 쓰기 시작했는데,
  `ScheduleTab`/`CostTab`은 아직 목업 id(`e1`~`e8`)를 기준으로 동작한다
  (`routineGenerator.js`의 `EXPERIENCE_SLOT`, `SCHEDULABLE_EXPERIENCES`).
  그래서 실제 체험을 담아도 일정표에 안 뜨고 체험비도 0원으로 나온다.
  크래시는 없다(빈 배열이라 NaN도 안 난다) — 조용히 연결만 끊긴 상태다.
  Playwright로 재현 확인함.
  → 다음 단계에서 두 탭을 연동할 때 **가장 먼저** 풀어야 할 문제다.
  가격이 API에 없으므로(§14) 체험비를 어떻게 계산할지도 같이 정해야 한다
  (사용자 입력으로 받을지, 체험비 항목을 없앨지 등 — 제품 판단 필요).
- **`ScheduleTab`은 아직 `UTILS` 목업을 직접 import한다.** 식당 데이터를
  실제로 바꾸려면 그 import부터 걷어내야 한다.
- **지도 좌표는 임시 변환이다.** 지도가 아직 목업(CSS 배경)이라 위경도를
  지역 bounding box 기준 백분율로 바꿔 핀을 찍는다
  (`toPercentCoords`). 실제 Kakao Map을 붙이면 이 변환은 통째로 없어지고
  `mapX`/`mapY`를 그대로 넘기면 된다.
- **숙소 예약 링크가 아직 고정 URL이다.** design 원본부터 모든 숙박
  카드가 `visitkorea.or.kr` 대표 주소로 갔는데, 이제 `contentId`가 있으니
  개별 상세 페이지로 보낼 수 있다. 다만 공식 상세 URL 형식을 확인하지
  못해 이번엔 그대로 뒀다.
- **개발 서버에서 `/api/*`를 쓰려면 `vite.config.js`의 dev 플러그인이
  필요하다.** `vercel dev`가 이 환경에서 안 되기 때문에(§3) 같은 핸들러
  파일을 Vite 미들웨어에서 직접 실행하도록 해뒀다. 배포 동작에는 영향이
  없고, 프로덕션 번들에 `TOUR_API_KEY`가 들어가지 않는 것도 확인했다.

⚠️ 사진 품질은 지역마다 편차가 크다. 홍성은 지역명 검색으로는 기념비·흉상·시장
내부뿐이라 "용봉산·남당항·홍주성·스카이타워" 등 명소 이름으로 다시 찾아야 했다.

### 적용 방식 — 런타임 호출 0건
지역 대표 사진은 `src/data/regionPhotos.js`에 URL 상수로 고정했다. 이유:

1. 홈 캐러셀·마이페이지 카드는 방문자마다 지역 수만큼 호출이 생긴다. 사진 한 장에
   일 1,000건 한도를 태울 이유가 없다.
2. 키워드 검색이라 부를 때마다 엉뚱한 지역 사진이 1등으로 올 수 있다(위 ⚠️).
   사람이 한 번 고르는 편이 결과가 안정적이다.
3. 저장하는 것은 이미지 URL(정적 참조값)이지 관광 콘텐츠 캐시가 아니다 —
   지역 코드·중심 좌표와 같은 성격이다.

실측(화면 진입 시 관광공사 API 호출 수):

| 화면 | 관광공사 API | 이미지 파일 |
| --- | --- | --- |
| 홈 | 0건 | 4장 |
| 지역 소개 | 0건 | 1장 |
| 마이페이지(저장 3곳) | 0건 | 3장 |
| 계획 화면 | 1건(area-based) | 5장 |

이미지 파일은 tong.visitkorea.or.kr에서 바로 받는 정적 파일이라 OpenAPI 호출
한도와 무관하다.
